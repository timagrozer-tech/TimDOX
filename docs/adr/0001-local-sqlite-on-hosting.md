# ADR-0001: База данных — локальный SQLite на хостинге вместо Supabase

**Статус:** Принято
**Дата:** 2026-10-09
**Решили:** владелец (полная свобода действий), Claude

## Контекст
Сайт переехал с Render на обычный хостинг Рег.ру (Москва, Passenger, несколько процессов).
База осталась в Supabase (Франкфурт): ~45 мс на запрос из Москвы, API делает 15–26 запросов к базе —
лента ~0,9 с, профиль ~0,6 с, `auth/me` ~0,3–0,8 с (журнал `req_log`). Данных 115 МБ, из них 96 МБ — файлы
(MEDIA_STORAGE=db), 25 пользователей.

## Решение
Перевести хостинг на локальный SQLite (`DATA_DIR/yarko.db`). При первом запуске новой версии один процесс
(под файловым замком) копирует все таблицы из Supabase во временный файл, сверяет число строк и
атомарно переименовывает. Supabase остаётся нетронутой копией на момент переезда. Ежедневная резервная копия
SQLite — на диск хостинга (хранятся 3 последних).

## Варианты
| | Supabase + кэш/пакетные запросы | **Локальный SQLite** | MySQL/PostgreSQL Рег.ру |
|---|---|---|---|
| Сложность | высокая (переписать десятки запросов) | низкая (приложение уже умеет SQLite) | средняя (база создаётся владельцем в панели, MySQL — новый диалект) |
| Скорость | лучше, но всё равно 45 мс × N | доли миллисекунды на запрос | ~1 мс на запрос |
| Участие владельца | нет | нет | нужно создать базу и пароль |
| Риски | — | одна запись за раз (WAL); резервные копии на нас | лишний сервис |

## Последствия
- Запросы к базе быстрее в десятки раз; файлы из базы читаются локально.
- Записи в Supabase после переезда не попадут в SQLite (Render в резерве, окно — секунды).
- Писатель в SQLite один за раз — при росте до тысяч активных пользователей вернуться к PostgreSQL (VPS).
- Откат: `YARKO_LOCAL_DB=0` в `yarko.env` — снова Supabase (без изменений, сделанных после переезда).
